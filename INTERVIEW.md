# fwsim: interview questions and model answers

25 questions an HDD-firmware interviewer could ask about this project,
grouped by topic. The answers are written the way you would say them out loud:
the claim first, then the reason, then a pointer to the code or a measured
number. Every number comes from `results/results.md`, generated by `make bench`
(see the README for the full table).

---

## Concurrency

### 1. Walk me through the threads in fwsim and what they share.

There are two threads. The **host** thread builds commands, submits them and
collects completions. The **firmware** thread does everything else: dequeue,
decode, cache, media, completion. They share very little, on purpose:

- the submission queue (host → firmware) and the completion queue
  (firmware → host);
- two flags, `power_on` and `stop_req` (atomics);
- the NCQ tag bitmap `tags_busy` (an atomic `uint32_t` updated with
  `fetch_or` / `fetch_and`);
- statistics counters (single-writer relaxed atomics).

The cache, the media, the disk-sim handle and the read-ahead state belong
only to the firmware thread, so they need no locks. That mirrors a real
controller, where one core runs the command and cache layer. The fewer
things are shared, the fewer things can race.

### 2. How does a command struct get from the host to the firmware without a lock on the struct itself?

Through **ownership transfer**. The host fills in the `fw_cmd_t` and then
pushes a pointer into the submission queue. The push does a
`memory_order_release` store of the tail index, and the firmware's pop does
an `acquire` load of it. Release/acquire guarantees that every write the
host made before the push (opcode, LBA, buffer, timestamps) is visible to
the firmware after the pop. From then on only the firmware touches the
struct, until it pushes it onto the completion queue, which is the same
handoff in reverse. Touching a command while the other side owns it would be
a data race. ThreadSanitizer checks this on every `make tsan` run and reports
nothing.

### 3. Prove your lock-free SPSC ring is correct.

Two counters run freely and never wrap modulo the capacity: `tail` is
written only by the producer, `head` only by the consumer. The number of
items is `tail - head` (unsigned, so it stays correct past 2^64), and the
slot is `n & (cap-1)`. Each counter has a single writer, so no
compare-and-swap is needed. Two ordering rules make it correct:

1. **Data before index.** The producer writes the slot and then
   store-releases `tail`. The consumer load-acquires `tail` before reading
   the slot. So when the consumer sees the new tail, it is guaranteed to see
   the slot's contents.
2. **Read before reuse.** The consumer reads the slot and then
   store-releases `head`. The producer load-acquires `head` before deciding
   a slot is free. So the producer can't overwrite a slot the consumer is
   still reading.

The ring is empty when `tail == head` and full when `tail - head == cap`.
Because the counters run freely, no slot has to be wasted to tell full from
empty. The tests cover full, empty and wrap-around, and they also start the
counters near `SIZE_MAX` to prove the arithmetic survives overflow. A
2-thread stress test checks ordering for 2 million items, and another test
checks that a struct published through the ring is seen completely.
See `src/ring_spsc.h`.

### 4. Why is `volatile` not enough?

`volatile` only tells the compiler "actually do this load or store; don't
keep the value in a register." It gives:

- **no atomicity**: a 64-bit volatile store can tear on some targets, and
  `x++` is still a separate load and store;
- **no ordering against other memory**: the compiler may still move the
  ordinary slot write after the volatile tail write, and nothing stops the
  CPU from doing it either. ARM reorders stores freely.

In the C11 memory model, a volatile access racing with another thread is
still a data race, which is undefined behaviour. `_Atomic` with
acquire/release gives atomicity and the exact ordering we need. On x86 those
compile to plain `MOV`s plus a compiler barrier, which is why they're cheap.
`volatile` is the right tool for memory-mapped device registers, not for
communication between threads.

### 5. Mutex vs condition variable: what's the difference, and why does your mutex queue have two condvars?

A **mutex** gives mutual exclusion: only one thread at a time is inside the
critical section. A **condition variable** lets a thread sleep until some
condition on the shared state might have changed, and it releases the mutex
atomically while it sleeps, so a waker can't slip in between "I checked"
and "I slept" (no lost wake-up).

There are two condvars because there are two different conditions:
consumers wait for "not empty" and producers wait for "not full". With only
one condvar, a `signal` meant for a producer could wake a consumer, which
finds nothing and goes back to sleep. Then the producer stays asleep. Every
wait is in a `while (!cond) wait()` loop, because of spurious wake-ups and
because another thread may grab the item first.

### 6. How much faster was the lock-free queue, and why?

Two measurements:

- **Raw 2-thread handoff**: 18.25 vs 0.69 million items/s, **26×** in favour
  of the lock-free SPSC ring (median of 5 runs).
- **The real firmware**, serving cache-hit READs: **56×** the command rate at
  QD 1 (1,177 vs 20.9 K commands/s; 0.66 vs 47.7 µs average latency), and
  2.3× at QD 32 (2,418 vs 1,038 K/s).

The difference comes from what each side does when the queue is empty. The
mutex version *blocks*: a futex syscall to sleep, then another to wake. A
sleep/wake cycle costs tens of microseconds on Linux, and at QD 1 every
single command pays it twice (submit and completion). The SPSC version
*polls* briefly, and a push is just two cache-line transfers. At QD 32 the
mutex queue is rarely empty, so fewer threads go to sleep and the gap
closes. The honest trade-off: lock-free polling burns CPU while it waits.
That's fine for a dedicated firmware core and wasteful on a shared machine.

### 7. What is false sharing and how did you avoid it?

Two threads write different variables that happen to sit on the same 64-byte
cache line, so the line keeps bouncing between their cores even though they
never touch each other's data. In the SPSC ring, `head` (consumer) and `tail`
(producer) are separated by explicit padding onto different cache lines.
I used padding arrays rather than `alignas(64)`, because `malloc` only
guarantees 16-byte alignment, so an over-aligned member inside a
heap-allocated struct isn't guaranteed to land on a line boundary. Padding
works regardless of the base address.

### 8. Your statistics counters are read by the host while the firmware updates them. How is that not a race?

They are `_Atomic uint64_t`, but each one is updated with a relaxed load plus
a relaxed store rather than `atomic_fetch_add`. That's correct because each
counter has exactly **one writer** (the firmware thread), so no increment
can be lost. It's also cheaper: `fetch_add` compiles to a `LOCK XADD`, which
is unnecessary with one writer. Relaxed ordering is enough because nothing
else is published through a counter; a reader just wants a recent value.
A plain `uint64_t` would be a data race (UB, and TSan would report it).

### 9. How do you detect an NCQ tag being reused while still outstanding?

There is a 32-bit atomic bitmap with one bit per tag. `fw_submit` does
`old = atomic_fetch_or(&tags_busy, 1u << tag)`. If the bit was already set in
`old`, the tag is in use and the command is rejected with `TAG_IN_USE`
(sense ABORTED COMMAND, 4Eh "overlapped commands attempted", the real SCSI
code). The firmware clears the bit with `fetch_and` *before* it posts the
completion, so a host that reuses the tag the moment it sees the completion
never gets a spurious rejection. The read-modify-write is atomic, so two
submitters racing for one tag can't both win.

## Caching

### 10. Explain your cache's data structure and complexity.

There is a fixed pool of N entries, one per sector, with the data in one
slab. A **hash map** (chained, about two buckets per entry, Fibonacci
hashing) maps LBA → entry in O(1). A **doubly linked list** with a sentinel
node keeps recency order (MRU at the front). Touching, unlinking and finding
the LRU end are all O(1). A singly linked list would need an O(n) walk to
unlink from the middle, and the sentinel removes every empty-list special
case. Nothing is allocated on the I/O path: entries come from a free list,
just as firmware has no general-purpose heap. A randomised test compares the
cache with a simple reference model over 50,000 operations and checks the
exact order after every operation.

### 11. Why Fibonacci hashing instead of `lba % buckets`?

LBAs are extremely regular: 4 KiB I/O on 512-byte sectors means every LBA is
a multiple of 8. With `lba % nbuckets` and a power-of-two `nbuckets`, those
LBAs only ever use 1/8 of the buckets. Multiplying by 2^64/φ and keeping the
top bits mixes every input bit into the index. A test inserts 1,000
strided LBAs and asserts the longest chain stays short.

### 12. What does LRU evict when the least-recently-used entry is dirty?

Never the dirty one. Its data exists nowhere else, so dropping it would lose
an acknowledged write. Eviction takes the least-recently-used *clean* entry.
If every entry is dirty, the insert fails and the write handler destages the
oldest eighth synchronously, then retries. That "forced destage" stalls the
command, which is why the watermark-driven background destage tries never
to let the cache get that full. An alternative design keeps separate clean
and dirty lists so eviction is O(1); I kept one list because it preserves a
single global recency order, which "destage the oldest dirty first" relies on.

### 13. Describe your destaging policy.

There are three triggers:

- **Threshold**: dirty ≥ 75% starts a destage *down to* 50%. The hysteresis
  matters: destaging just below 75% would trigger a one-sector destage on
  every write, and batches would never be big enough to sort well.
- **FLUSH**: destage everything.
- **Idle**: after 50 ms of drive time with no commands, start destaging.

Each batch is the oldest dirty entries, which are the ones least likely to be
rewritten soon. The batch is **sorted by LBA**, so N random seeks become one
sweep across the disk, and **coalesced**, so adjacent sectors become one
media write. Background batches run as a "plan" executed two media writes at
a time between host commands, so a host command waits for at most two
destage writes, not a 1,000-sector destage. The plan stores LBAs, not
pointers, and re-checks each one, because by the time it gets there the
entry may have been rewritten, cleaned by a FUA write, or even evicted and
reused.

### 14. What did sorting the destage by LBA buy you?

On sustained random 4K writes in write-back mode, LBA-sorted destage reached
151.1 IOPS vs 72.0 for age-order destage, **2.1×**, both measured including
the final FLUSH. p99 latency halved too (68 vs 137 ms). The seek time per write drops
because consecutive destage writes are close together on the platter: a
SCAN/elevator sweep instead of random jumps. That's the same reason disk-sim
showed SPTF and SCAN beating FCFS.

### 15. How does read-ahead work, and why did it need "streaming" to show any benefit?

If a read starts exactly where the previous one ended, the stream is
probably sequential, so after posting the completion the firmware reads the
next 256 sectors into the cache. Read-ahead first "helped" only on paper:
the hit rate was 99.9%, but throughput didn't change. The prefetch was
issued after the host's turnaround, by which time the next sector had
already passed under the head, so it paid a near-full revolution. Real
drives avoid exactly this by **keeping the read channel streaming into the
buffer**. I modelled that: a prefetch that continues the previous read
starts at the instant that read ended. Sequential 64 KiB reads at QD 1 then
went from 108 to 743 IOPS (**6.9×**), with a 99.9% hit rate. Without read-ahead, every QD-1
command loses about one revolution (8.3 ms at 7,200 rpm).

### 16. Why can write-back make p99 latency *worse*?

On random 4K writes confined to 1 GiB, write-back had a far better median
(0.03 ms vs 24 ms) but a *worse* p99: **56 ms vs 36 ms** for write-through.
The reason is background destaging. Once the cache passes its high
watermark, every host command waits for up to two destage writes, so the
unlucky commands pay for media work that write-through would have spread
evenly. Write-back moves media work out of the write path, but it doesn't
make that work disappear. It shows up as queueing for whatever command
comes next. (On the cache-friendly mixed workload it was the other way round:
p99 19 vs 24 ms, because most I/O hit the cache.) Real firmware tunes this
with read-priority scheduling, smaller destage slices, adaptive watermarks,
or by pausing destage while host I/O is queued. Those would be the next
experiments here.

## Durability

### 17. What exactly do FLUSH and FUA guarantee?

- **FUA** (Force Unit Access) on a write: *this write's* data is on
  non-volatile media before the drive acknowledges it.
- **FLUSH CACHE**: every write *acknowledged before the FLUSH was issued* is
  on non-volatile media before the FLUSH completes. It says nothing about
  writes acknowledged while the FLUSH was running.

My power-loss checker models exactly that. When it issues a FLUSH it
snapshots the per-block acknowledged versions, and only that snapshot
becomes "promised durable" when the FLUSH completes. Then it checks two
separate things: *lost* (the latest acknowledged version is gone, which
write-back caching legitimately allows) and *violation* (a promised-durable
version is gone, which must never happen). It found zero violations in
every mode, in every trial.

### 18. Summarise the power-loss results.

There were 100 trials per mode, each cutting power at a random moment 50–
1000 ms (drive time) into a random-write workload:

- **Write-back without FLUSH**: lost acknowledged writes in **100/100**
  trials, **351.5 per trial** on average (max 383) out of ~525
  acknowledged. Acknowledged ≠ durable.
- **Write-back + FLUSH every 32 writes**: 18.5 lost per trial (max 31):
  only writes acknowledged since the last completed FLUSH. Zero durability
  violations.
- **Write-back + FUA on every write** and **write-through**: **zero** lost
  acknowledged writes in 200 trials.
- **The cost**: acknowledged-write throughput of 1,400 IOPS (write-back),
  284 (FLUSH), 182 (FUA) and 176 (write-through), so write-through was 7.9×
  slower than write-back over these short bursts.

Across all 400 trials there were 0 durability violations and 0 unreadable
sectors after reboot.

### 19. What is a torn write and how does your simulator produce one?

A multi-sector write interrupted part-way: some sectors are new and the rest
are old. When power is cut during a media access, the media layer works out
how many sectors had already passed under the head (elapsed time minus seek
and rotation, divided by time per sector) and writes only those. The test
writes 2,048 sectors in write-through mode, cuts power mid-transfer, and
checks after reboot that the result is a clean **prefix** (new sectors, then
only untouched ones), and that the command was never acknowledged. A single
sector is atomic, as it is on real drives.

### 20. How do real drives avoid losing the write cache on power loss?

Most HDDs don't: their DRAM cache is volatile. That's why OSes and
filesystems issue FLUSH/FUA at commit points, and why `hdparm -W0` exists
for databases that don't trust them. Enterprise drives and SSDs add
**power-loss protection**: capacitors (or, on some HDDs, the spinning
platters' back-EMF) supply enough energy to write the cache contents to
flash or to a reserved media area during the power-down. With PLP the drive
can treat the cache as non-volatile and report it that way. fwsim models the
consumer case: no PLP.

## CRC, ECC and media errors

### 21. What's the difference between CRC and ECC, and which one does a real drive use?

- **CRC** *detects* errors. It's a polynomial remainder, cheap, and has
  guarantees: all single- and double-bit errors, all odd-weight errors, and
  every burst up to its width.
- **ECC** *corrects* errors by adding redundancy, at a higher cost.

Real HDDs use strong ECC (LDPC today, Reed-Solomon earlier) in the read
channel, over 4 KiB sectors, *plus* an end-to-end CRC or protection
information on the data path to catch corruption in buffers, on buses or in
firmware. fwsim implements the CRC layer and models read-channel noise as
transient bit flips that a retry clears. Uncorrectable media is modelled as
a persistent flip, which becomes MEDIUM ERROR after N retries.

### 22. Why do you include the LBA in the CRC?

To catch **misdirected** reads and writes: correct data in the wrong place.
A CRC over the data alone would accept a perfectly valid sector stored at the
wrong LBA. Seeding it with the LBA makes that record fail its check. A test
copies LBA 300's record into LBA 301's slot and gets MEDIUM_ERROR at 301.
T10 Protection Information's "reference tag" exists for the same reason.

### 23. Walk me through what happens on a CRC mismatch.

1. The media layer re-reads the sector on later revolutions, up to N times
   (default 3; each retry costs one revolution of drive time).
2. If a retry passes, the error was transient: count it as recovered and
   return the data.
3. If all retries fail: never return data we know is wrong. Fail the
   command with `MEDIUM_ERROR` (sense 03h/11h00h, unrecovered read error),
   put the failing LBA in `err_lba` (the sense "information" field), and add
   the LBA to a **pending** list.
4. The next time the host *writes* that LBA, the firmware reallocates it to
   a spare sector via disk-sim's `disk_add_grown_defect()` (the G-list), and
   later accesses pay the extra seek to the spare area.

The data isn't moved at read time because the host still believes the sector
holds its data. Reallocating only when fresh data arrives means nothing is
silently replaced. In the benchmark, every injected persistent flip produced
a MEDIUM_ERROR at exactly the injected LBA (25/25), every transient flip
was recovered (20/20), and there were zero silent corruptions in 20,000
sector reads.

## C details

### 24. Why a function-pointer dispatch table instead of a switch?

`static const fw_handler_t dispatch[FW_OP_COUNT] = { [FW_OP_READ] = h_read, ... }`
uses C99 designated initialisers, so the table reads like a spec and
unlisted opcodes are automatically `NULL`. Decoding a command is a bounds
check plus one indirect call however many opcodes there are. Adding a
command is one line plus a handler. `opcode` is a `uint8_t` in the command
struct, not the enum type, so tests can send genuinely invalid opcodes (0xFF)
without undefined behaviour. They get `INVALID_OPCODE` (ILLEGAL REQUEST
20h). The usual caveat applies: a switch lets the compiler inline handlers,
and a table makes control flow harder for static analysis to follow.

### 25. Name some C pitfalls you had to handle explicitly.

- **Integer overflow in range checks**: `lba + count > capacity` can wrap
  around. I check `lba >= cap || count > cap - lba` instead, and a test sends
  `lba = UINT64_MAX - 1`.
- **Unaligned access**: copying the IDENTIFY payload out of a `uint8_t[]`
  with a pointer cast would be misaligned (UBSan flags it), so it uses
  `memcpy`.
- **Short reads and writes**: `pread`/`pwrite` may transfer less than asked,
  so both loop. Reading past EOF of the sparse file returns zeros.
- **Lazy initialisation race**: the CRC table is built under `pthread_once`.
  A plain `if (!init)` would be a data race, and a test hammers it from 8
  threads at startup.
- **Clock choice**: `CLOCK_MONOTONIC` everywhere, including
  `pthread_condattr_setclock` for timed waits, because `CLOCK_REALTIME` can
  jump.
- **Use after handoff**: `process()` copies `opcode`, `lba` and `count` out
  of the command *before* posting the completion, because afterwards the
  host owns the struct and may already be reusing it.
- **Sanitizers in CI-style targets**: `make asan` (ASan + UBSan with
  `-fno-sanitize-recover`) and `make tsan` both run the whole suite for both
  queue implementations, and report nothing.
